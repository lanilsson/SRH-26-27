## 2. Details still to clarify (your decisions)

**D1. Homophily measure: the Elliptic result conflicts with the expectation.**
*Deferred 2026-10-11, tracked as OI-1 in [open-issues.md](open-issues.md).*
Build Procedure step 2 says the measurement will "confirm that it is
heterophilous". The edge-homophily ratio named there (Zhu et al., 2020) gives:

- Elliptic overall: **0.954** (labelled–labelled edges)
  - edges from fraud nodes: **0.541** of labelled neighbours are fraud
  - edges from licit nodes: **0.976** of labelled neighbours are licit
- IEEE-CIS-G: the 1-hop ratio is **undefined**, because every edge joins a
  transaction and a metadata node. Over 2-hop pairs (transactions sharing a
  metadata value, counted once per shared value) it is **0.859**.
- H²GB reports other measures on IEEE-CIS-G (H_edge 0.5917, H² Index 0.9846,
  where values near 1 mean heterophilic; Lin et al., Table 2), so the numbers
  are not directly comparable.

Decide which measure(s) the study reports, how the IEEE-CIS-G measure is
defined given the bipartite structure, and what this means for the framing.
Some measures correct for class imbalance (for example class-insensitive
homophily, Lim et al., 2021). Read them yourself before choosing.

**D2. Elliptic has 165 features, not 166.** PyG's built-in loader, which the
proposal now names, drops the time-step column, leaving 165 features.
Weber et al.'s "166" counts the time step. Update the number in the proposal,
or decide to add the time step back.

**D3. Architecture details** (draft in `src/models/gcn.py`, which matches
"input layer, two aggregation layers, output layer"):

- Input layer: Linear(features → hidden_dim) for transactions, and a learnable

- The ego, 1-hop and 2-hop channels are **concatenated**, then mixed by one
  linear layer per aggregation layer. Parameter counts therefore differ by
  configuration (Elliptic, hidden 64: 19k / 27k / 27k / 35k). That comes with
  the mechanisms, but it deserves one sentence in the paper.
- 2-hop channel: see D8.

**D8. The 2-hop operator counts paths instead of using 0/1 entries.**
*Decided 2026-10-11: keep path counts on both datasets. Note the difference from H2GCN in the paper.* H2GCN
marks each exact-2-hop pair 0/1. On IEEE-CIS-G, card4 / card6 / ProductCD
values are each shared by tens of thousands of transactions, so the 0/1
two-hop matrix would have ~10¹⁰ entries and can't be built. The draft
instead weights each 2-hop pair by its number of shared neighbours.

- Elliptic: computed explicitly.
- IEEE-CIS-G: computed implicitly as A(Ah) − deg·h, which is exact because the
  graph is bipartite. Tests check that the two methods agree.

Both datasets use the same definition. Confirm it, and note the difference
from H2GCN.

**D9. IEEE-CIS-G feature preprocessing departs from H²GB, as your proposal
requires.** H²GB z-scores over *all* transactions and then applies PyG
`NormalizeFeatures` (each row sums to 1). The first uses validation/test
statistics; the second would undo standardisation. Following Build Procedure
step 1, both are replaced by standardisation over training transactions only
(H²GB's NaN → 0, one-hot encoding and log of TransactionAmt are kept). This is
worth one sentence in the paper, since it isn't H²GB's exact feature pipeline.

**D10. 464 of 4,785 IEEE-CIS-G columns are constant over training
transactions**
*Decided 2026-10-11: drop them, so the feature dimension is 4,321. Applied in `src/data/ieee_cis_g.py`.*
, mostly categories (e.g. DeviceInfo values) that first appear
later in time. 425 of them are nonzero in val/test rows. The model can't learn
anything about them, but their untrained weights still feed into val/test
predictions. Possible choice: drop columns that are constant over the training
rows (decided from training data only, so no leakage).

**D11. "Loaded through the open-source H²GB library."** The `H2GB` package
(0.1.0) is not used directly:

- it targets Python 3.9 / PyTorch 2.0.1 / PyG 2.5 and brings unpinned
  dependencies (torch_sparse, ogb, wandb, …) that would break the pinned
  environment;
- its dataset class doesn't contain the split, which lives in its training
  loader.

`src/data/ieee_cis_g.py` reproduces its construction from the source code and
matches every published count (section 3). Decide whether to reword the
proposal ("graph built following the H²GB construction code") or to install
the library anyway.
